# 05. セキュリティ・法令対応

患者の氏名・ID・生年月日・診療情報を扱うため、設計段階から織り込む。

> **免責:** 以下は技術設計上の整理であり、法的助言ではありません。
> 実際の運用開始前に、院内の個人情報保護管理者・情報システム部門の承認を得てください。

## 5.1 準拠すべき枠組み

| 枠組み | 関係する内容 |
|---|---|
| 個人情報保護法 | 要配慮個人情報（病歴）の取扱い。安全管理措置の義務 |
| 医療情報システムの安全管理に関するガイドライン（厚労省） | 医療機関向けの技術・運用要求。**最新版を確認すること**（第6.0版系が現行だが改定が続いている） |
| 院内の個人情報保護規程 | 最終的にはこれが基準 |

**確認事項:** 院内で新規システムを導入する際の審査プロセス（医療情報部の承認、倫理審査の要否）。

## 5.2 完全オフラインの担保

### 「ブラウザで動く」＝「インターネットに繋がる」ではない

本システムはUIをブラウザで表示するが、**インターネット接続は一切不要**。
用語が誤解を招きやすいため、説明の際は以下を明確にする。

| 用語 | 実際の意味 |
|---|---|
| ブラウザ | 画面を表示する道具。ネット接続とは無関係に使える |
| Webアプリ | 「画面をブラウザで作る」という作り方の呼び名。ネットに出る意味ではない |
| **localhost** | **PCが自分自身と通信するための仕組み。データはPCの外に一切出ない** |

Phase 1（単独運用）では、アプリが自分のPCの中でだけ通信し、その画面をブラウザに映す。
PCの外——院内ネットワークにもインターネットにも——データは流れない。
ネットワークケーブルを抜いた状態、Wi-Fiを切った状態で全機能が動作する。

Phase 2（複数人共有）では院内LAN内のみで通信する。この場合もインターネットには出ない。

#### 情報システム部門への説明用の要点

- インターネット接続を必要としない。外部サーバー・クラウドサービスを一切使わない
- 外部への通信を行うコードを含まない（下記のテストで継続的に検証する）
- OCRモデル・辞書・フォント・グラフ描画ライブラリはすべて製品に同梱。実行時のダウンロードなし
- 自動更新機能を持たない
- Phase 1 では通信先が `localhost`（自PC内）のみ。ファイアウォールの穴開けも不要

「外部通信しない」は方針では足りない。**実装とテストで担保する。**

### 設計ルール

1. HTTPクライアントライブラリ（requests, httpx, urllib）を業務コードで使わない
2. OCRモデル・辞書・フォント・JSライブラリはすべてリポジトリまたはインストーラーに同梱。
   実行時ダウンロードを行うライブラリ設定は明示的に無効化する
   （例: PaddleOCR / HuggingFace 系はモデル自動DLがデフォルトなので、必ずローカルパス指定に固定）
3. 各ライブラリのテレメトリ・使用状況送信をオフにする
4. 更新チェック機能を実装しない

### テストでの検証

```python
# tests/test_offline.py
def test_no_network_access(monkeypatch):
    """全パイプラインを通し、ソケット接続が一度も発生しないことを検証する。"""
    def deny(*args, **kwargs):
        raise AssertionError("ネットワーク接続が試行されました")
    monkeypatch.setattr(socket.socket, "connect", deny)
    monkeypatch.setattr(socket.socket, "connect_ex", deny)

    run_full_pipeline(SAMPLE_PDF)   # 例外なく完走すること
```

これをCIで常時回す。ライブラリ追加で意図せず通信が入るのを防げる。

### 受入時の実証

デモ時にPCのネットワークを物理的に切断した状態で全機能を動かす。
「オフラインで動く」を口頭ではなく実演で示す。

## 5.3 保存データの保護

| 対象 | 方針 |
|---|---|
| 患者氏名・生年月日 | アプリケーション層で暗号化して保存（鍵はOS資格情報ストア/DPAPIで保護） |
| 患者ID | 検索に使うためハッシュ化はせず、DB全体の保護で担保 |
| 原本PDF | アクセス権を制限したフォルダに保管。パスをDBで管理 |
| DBファイル（SQLite期） | ディスク暗号化（BitLocker）を前提とする |
| バックアップ | 暗号化した上で院内保管。**クラウドバックアップは使わない** |

**Phase 2 でPostgreSQLへ移行する際は、接続にTLSを使い、DBサーバーを院内LAN内に限定する。**

## 5.4 アクセス制御・監査（Phase 2）

| 役割 | 権限 |
|---|---|
| 管理者 | 全操作、ユーザー管理、プロファイル編集 |
| 技師 | レポート取り込み、抽出結果の確認・修正、出力 |
| 医師 | 閲覧、コメント入力 |
| 閲覧のみ | 閲覧 |

- 認証は院内Active Directory連携が理想。難しければアプリ内アカウント＋パスワードポリシー
- `audit_logs` に「誰が・いつ・どの患者のデータを・どう操作したか」を記録
- 監査ログは削除不可（アプリからの削除APIを実装しない）

## 5.5 開発・検証時のルール

**最重要。** 開発中の事故のほうが起きやすい。

| ルール | 理由 |
|---|---|
| 実患者データをクラウドAI・外部サービスにアップロードしない | Claude Code含む。設計・実装の相談は匿名化した情報のみ |
| サンプル帳票は必ず黒塗り or ダミー化してから配置する | 氏名・ID・生年月日・住所・電話番号 |
| `samples/` を `.gitignore` に入れる | 誤コミット防止 |
| コミット前に個人情報のスキャンをかける | pre-commitフックで氏名パターン等を検出 |
| テストデータは合成データを使う | 実データに依存したテストを書かない |
| スクリーンショットもマスキング対象 | 資料・報告書に貼る画像に注意 |

### 黒塗りの注意点（テキストPDFの場合）

**PDFに黒い矩形を重ねただけでは元テキストが残る。** コピー&ペーストで復元できてしまう。
テキストレイヤーを持つPDFでは特に注意が必要。

一方で、**印刷してマーカーを引きスキャンし直す方法は使えない。**
テキストレイヤーが失われ、検証したい対象そのものが壊れてしまうため。

推奨する順序:

1. **そもそも共有しない**（最も安全）。開発者本人のPC内で処理が完結するなら、
   黒塗りせずにローカルで扱う。外部に渡さないなら黒塗りは不要
2. **ラベル一覧だけを共有する**。抽出ルールの作成に必要なのは帳票の「項目名」であって
   「患者の値」ではない。テキストを抽出し、項目名の一覧だけを取り出せば個人情報は含まれない
   （[06](06-roadmap.md) の手順を参照）
3. どうしてもPDFごと渡す必要がある場合のみ、**PDFの墨消し（redaction）機能**を使い、
   テキストを実際に削除する（描画の上書きではなく削除であることを確認する）

## 5.6 リスクと緩和

| リスク | 影響 | 緩和策 |
|---|---|---|
| OCR誤認による誤った値のカルテ転記 | **臨床判断への影響。最大リスク** | 信頼度による要確認フラグ、人による確定必須、元PDF該当箇所の並置表示、前回値との整合チェック |
| 抽出漏れによる異常の見落とし（ERI/EOL等） | 電池切れの見落とし | 重要項目は抽出失敗時に必ず赤フラグ。未確認レポートの一覧表示 |
| 患者の取り違え | 誤った患者のカルテに転記 | 患者ID・氏名・生年月日の3点照合。デバイスシリアル番号との紐付け確認 |
| DBファイル破損 | データ消失 | 定期バックアップ、SQLite共有アクセスの禁止 |
| 端末紛失・持ち出し | 情報漏洩 | ディスク暗号化、院内PC限定の運用 |
| メーカーの帳票改版で抽出が壊れる | 静かに精度が落ちる | 抽出失敗率のモニタリング。プロファイルのバージョン管理 |

## 5.7 USB経由のファイル持ち込み

[02.2](02-architecture.md#22-ネットワーク構成とデータ動線) の通り、レポートPDFは
インターネット系ネットワークからUSBメディアで電子カルテ系（閉域）へ持ち込む。

**これは本システムで最もリスクの高い経路。** 国内の医療機関では、閉域ネットワークへの
外部メディア持ち込みや保守回線を起点とするランサムウェア被害が複数発生しており、
診療停止に至った事例もある。

### 決定事項

**院内専用のUSBメディアを使用する。** 私物・ベンダー配布品・来訪者持参のメディアは使わない。
これは安全側の判断として妥当（メディアの出所が管理されていることが、この経路の前提になる）。

引き続き情報システム部門に確認すべきこと:

- 電子カルテ系ネットワークへのUSB接続について、追加の条件が課されていないか
  （台帳管理、事前ウイルスチェック、使用者の限定 など）
- 既にファイル受け渡し用の仕組み（受け渡し専用端末、一方向ファイル転送装置など）が
  用意されていないか。**あればUSBより安全なのでそちらを優先する**

### 本システム側で守ること

| 項目 | 方針 |
|---|---|
| 取り込みは読み取りのみ | USBメディアへの書き込み・削除を行わない。原本はメディア上に残したまま、院内ストレージへコピーする |
| 受け付けるのはPDFのみ | 拡張子ではなくファイル先頭のマジックナンバー（`%PDF-`）で判定。それ以外は無視 |
| PDF内の能動的要素を実行しない | JavaScript・埋め込みファイル・自動アクションを解釈しないライブラリ構成にする（pypdfium2は描画のみでJSを実行しない） |
| 自動取り込みしない | メディア挿入で勝手に処理を始めない。人が明示的に取り込み操作を行う |
| 取り込みログを残す | いつ・誰が・どのファイルを取り込んだか（ファイル名とSHA-256）を記録 |
| 異常なファイルは隔離 | パース失敗・サイズ異常は処理せず記録のみ |

### 運用側で守ること

- 院内専用メディアのみを使う（決定済み）。**専用メディアをインターネット系PCに挿す時点で
  汚染されうるため、「専用だから安全」ではない**点に注意する
- 持ち込み前にインターネット系PCでウイルススキャンをかける
- レポートPDF以外のファイルをメディアに入れない
- 使用後にメディア内のデータを消去する（患者情報が残ったまま放置されない運用にする）

**本システムはUSBのリスクを下げることはできても、無くすことはできない。**
最終的な可否判断は情報システム部門に委ねる。

## 5.8 「静かに壊れる」への備え

帳票レイアウトが変わったとき、システムは**エラーを出さずに抽出率だけ下がる**。
これが一番危ない。日次/週次で「抽出失敗率」「要確認率」を集計し、
急上昇したらUIに警告を出す仕組みを Phase 2 で入れる。
