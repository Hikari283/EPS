## 3.2 [A] テキストレイヤー優先（重要）

**現行運用は「印刷→スキャン」だが、これは技術的には自傷行為**にあたる。
各社システムからPDFを直接ダウンロードすれば、テキストレイヤーが残りOCRが不要になり、
抽出精度は劇的に上がる（誤認識がゼロになる）。

そのため実装は最初からハイブリッドにする:

```python
def load_tokens(pdf_path: Path) -> tuple[list[OcrToken], Source]:
    """テキストレイヤーがあればそれを使い、なければOCRにフォールバックする。"""
    text_tokens = extract_text_layer(pdf_path)
    if is_usable(text_tokens):        # 文字数・カバー率で判定
        return text_tokens, Source.TEXT_LAYER
    return run_ocr(pdf_path), Source.OCR
```

下流の抽出ロジックは `OcrToken` のリストしか見ないので、どちらでも同じコードが動く。

### ネットワーク分離があっても成立する

院内はインターネット系と電子カルテ系が分離されており、
各社システムから電子カルテ側へネットワーク経由でPDFを流すことはできない。
しかし **USBメディアで運んだPDFはテキストレイヤーを保持したまま届く**
（[02.2](02-architecture.md#22-ネットワーク構成とデータ動線)）。

避けたかったのは「紙にすること」であって、ネットワーク直結は手段にすぎない。
USBコピー1回で、全レポートの印刷+スキャンが不要になる。

### 決定: PDFの直接取得が可能

各社システムからレポートをPDFファイルとして取得できることを確認済み。
したがって **「印刷→スキャン」工程は廃止し、テキストレイヤー経路を主経路とする。**

これによる影響:

| 項目 | 変化 |
|---|---|
| 抽出精度 | 文字の誤認識が原理的に発生しなくなる。M1最大のリスクが消える |
| 前処理（[3.3](#33-c-前処理)） | 主経路では**不要**。傾き補正・二値化・ノイズ除去は書かなくてよい |
| OCRエンジン選定 | 主経路では不要。フォールバック用に1つあればよく、比較検証の優先度が下がる |
| M1の性格 | 「OCR精度の検証」から「テキストPDFからの項目抽出ルール作成」へ。不確実性が大幅に低下 |
| サンプル帳票 | スキャン品質を再現する必要がなくなる。ラベル一覧があればプロファイルを書ける |

**ただしOCR実装は捨てない。** 以下のケースで必要になるため、フォールバック経路として残す:

- 一部のメーカーが画像ベースのPDFしか出力しない場合（**要確認**。下記）
- 既に印刷・スキャン済みの過去レポートを遡って取り込む場合
- 将来メーカーの出力仕様が変わった場合

### 要確認: 「PDFが取得できる」≠「テキストレイヤーがある」

システムによっては、レポート画面を画像としてレンダリングしたPDFを出力する。
この場合、拡張子はPDFでも中身は画像であり、OCRが必要になる。

**確認方法（ツール不要・10秒）:** 保存したPDFをビューアで開き、

1. 本文の文字をドラッグして**選択できるか**
2. `Ctrl+F` / `Cmd+F` で、画面に見えている単語を**検索してヒットするか**

どちらもできればテキストレイヤーあり。できなければ画像PDFでOCRが必要。
**メーカーごとに結果が異なりうるため、5社すべてで確認する。**

## 3.3 [C] 前処理

スキャン品質が精度を最も左右する。エンジン選定より効く可能性が高い工程。

| 処理 | 目的 | 手法 |
|---|---|---|
| 解像度正規化 | OCRが想定する文字サイズに揃える | 300dpi相当にリサイズ |
| グレースケール化 | — | — |
| 傾き補正 (deskew) | スキャン時の傾きを除去 | Hough変換 or 最小外接矩形で角度推定 → 回転 |
| ノイズ除去 | スキャンのゴマ塩・にじみ | メディアンフィルタ / モルフォロジー |
| 二値化 | 文字と背景の分離 | 適応的二値化（大津法は網掛け背景に弱い） |
| 罫線除去（任意） | 表罫線が文字に接触して誤認するのを防ぐ | 水平/垂直方向のモルフォロジーで線を検出し除去 |
| 天地判定 | 上下逆スキャンの救済 | OCRを0°/180°で試し信頼度の高い方を採用 |

**すべての前処理をON/OFFできる設定にする。** 帳票によっては前処理が逆効果になるため、
[3.8](#38-精度評価の仕組み) の評価スクリプトで組み合わせを実測して決める。

## 3.4 [E] メーカー判別

各プロファイルYAMLに識別ルールを持たせ、1ページ目のトークン列に対してスコアリングする。

```yaml
identify:
  any_of:
    - "CareLink"
    - "Medtronic"
    - "メドトロニック"
  min_score: 1
```

- 最高スコアのプロファイルを採用
- どれもヒットしない／同点の場合はUIで手動選択させる（黙って推測しない）

## 3.5 [F] ラベルアンカー抽出

固定座標に依存しない中核ロジック。

### 考え方

帳票のレイアウトはメーカー・改版・スキャンのズレで変わるが、
**「ラベル文字列の隣（または下）に値がある」という関係は変わらない。**
そこでラベルを画像内で探し、その位置を起点に値を探す。

### フィールド定義（YAML）

```yaml
fields:
  battery_remaining_months:
    labels:                          # 表記ゆれをすべて列挙
      - "バッテリ残存"
      - "バッテリー残存期間"
      - "推定残存期間"
      - "Longevity"
      - "Remaining Longevity"
    label_match: fuzzy               # exact | fuzzy | regex
    fuzzy_threshold: 0.80            # OCR誤認を吸収
    direction: right                 # right | below | left | above
    window:                          # ラベルbboxからの相対探索範囲
      width_ratio: 3.0               #   ラベル幅の3倍先まで
      height_ratio: 1.5              #   行の高さの1.5倍まで縦にずれてもよい
    value_pattern: '(\d+(?:\.\d+)?)\s*(?:年|ヶ月|months?|yrs?)'
    unit_map:                        # 単位を正規化
      年: months_x12
      yrs: months_x12
      ヶ月: months
      months: months
    type: float
    range: [0, 240]                  # 値域チェック（外れたら信頼度を下げる）
```

### アルゴリズム

```
1. labels の各候補について、OCRトークン列から一致箇所を探す
   - fuzzy の場合は正規化編集距離で閾値以上を候補とする
   - 複数トークンにまたがるラベル（「バッテリー」「残存」が別トークン）に対応するため、
     近接トークンを連結した n-gram も候補にする
2. ヒットしたラベルbboxを起点に direction/window で探索窓を作る
3. 窓内のトークンを value_pattern でフィルタ
4. 残った候補を「ラベルからの距離」でソートし、最も近いものを採用
5. 該当なしなら fallback ルール（3.6）へ
```

### なぜfuzzyが必要か

OCRは「バッテリー」を「ハッテリー」「バッテリ一」（長音記号→漢数字の一）と読むことがある。
完全一致だけだと1文字の誤認で抽出が丸ごと失敗する。

### 注意点: 誤爆のリスク

fuzzy閾値を緩めると別のラベルに誤ヒットする。
**閾値は評価スクリプトで実測して決める**（勘で設定しない）。
また、同一ラベルが複数箇所にある場合（心房/心室で同じ項目名が並ぶ表など）は、
セクション見出しをスコープとして先に特定する仕組みが必要になる:

```yaml
  atrial_impedance:
    scope:                           # このセクション内でのみ探す
      labels: ["心房", "Atrial", "A."]
      extent: below                  # 見出しより下、次の見出しまで
    labels: ["インピーダンス", "Impedance"]
    ...
```

## 3.6 フォールバック戦略

ラベルが見つからない場合の段階的な救済:

| 順 | 手法 | 説明 |
|---|---|---|
| 1 | ラベルアンカー | 上記の主方式 |
| 2 | 相対アンカー | 別の抽出済みフィールドからの相対位置で探す |
| 3 | 領域＋パターン | ページの相対座標領域を指定し、その中でvalue_patternに合うものを拾う |
| 4 | 諦める | `null` + 理由コードを返し、UIで手入力を促す |

**4は失敗ではなく正常な結果。** 無理に値をでっち上げるより、空欄で人に渡すほうが安全。

## 3.7 [H] 信頼度の設計

各フィールドに 0.0–1.0 の信頼度を付ける。

```
confidence = w1 * ocr_confidence        # そのトークンのOCR信頼度
           + w2 * label_match_score     # ラベル一致度（fuzzyの類似度）
           + w3 * pattern_fit           # value_patternへの適合度
           + w4 * range_fit             # 値域内か（外れ値なら大きく減点）
           + w5 * consistency           # 前回レポートからの変化量の妥当性
```

`consistency` は特に有効。バッテリー残存が前回60ヶ月→今回600ヶ月ならOCR誤認（桁誤り）が濃厚。
**過去データを持つ一元管理システムだからこそ使える検算**であり、
単体のPDF変換ツールに対する明確な優位点になる。

### 閾値と扱い

| 信頼度 | UI表示 | 挙動 |
|---|---|---|
| ≥ 0.90 | 通常表示 | そのまま採用 |
| 0.70–0.90 | 黄色ハイライト | 要確認。確認チェックなしでは確定できない |
| < 0.70 | 赤ハイライト | 未入力扱い。人が入力する |

**全項目が緑でも、確定操作は必ず人が行う。** 自動確定は実装しない。

## 3.8 精度評価の仕組み

Phase 0 の主目的。これがないとエンジン選定も閾値決定も勘になる。

```
├─ redacted/

│  └─ abbott_001.pdf
└─ groundtruth/
   ├─ medtronic_001.csv     # field,value  を人手で作成

```

```bash
# エンジン・前処理の組み合わせを変えてフィールド単位の正解率を出す
python -m cli.eval --engine tesseract --preprocess deskew,binarize
python -m cli.eval --engine paddle    --preprocess deskew,binarize,delines
```

出力: フィールド別の正解率、誤りの実例、処理時間。
**この数値をもってOCRエンジンと前処理の組み合わせを決定する。**

## 3.9 実装順序

1. `OcrToken` / `ExtractionResult` のデータ構造を定義（コントラクトを先に固める）
2. PDF→画像、テキストレイヤー検出
3. Tesseractラッパー
4. 評価スクリプト（正解率が測れる状態を最優先で作る）
5. 前処理を1つずつ足して、評価スクリプトで効果を確認
6. ラベルアンカー抽出エンジン
7. 1メーカー分のプロファイルを作り込む
8. 残りメーカーへ横展開

**4を先に作るのが重要。** 測定できない状態で精度改善を進めると、
何が効いたのか分からないまま時間を溶かす。
