# 01. 要件定義

## 1.1 背景

院内でCIED（ペースメーカー、ICD、CRT-P/D、ILR等）の遠隔モニタリング業務を行っている。

現状のフロー:

```
各社リモートモニタリングシステム
  → レポートを印刷
  → 紙をスキャンしてPDF化
  → PDFを目視しながら必要項目を手作業でカルテに転記
  → Drへ共有
```

課題は「転記に時間がかかる」「Drとの共有が属人的」の2点。

## 1.2 目的

1. レポートPDFから必要項目を自動抽出し、カルテ転記の時間を短縮する
2. 抽出結果を一元管理し、Drが必要なときに参照できる状態にする
3. 100台以上のデバイスの経過を横断的に見られるようにする（トレンド把握・フォロー漏れ防止）

## 1.3 スコープ

### 対象患者

**院内でCIEDを植込み・管理している全患者。** 遠隔モニタリングの利用有無を問わない。

| 区分 | データの入り方 |
|---|---|
| 遠隔モニタリング中 | 各社システムからのレポートPDFを取り込む（主経路） |
| 遠隔なし（外来チェックのみ） | 外来チェック結果を手入力、またはプログラマ出力レポートを取り込む |
| 遠隔を中止した患者 | 中止日・理由を記録し、以後は外来扱い |

遠隔なし患者も登録することで、本システムは院内CIEDの**台帳**として機能する（FR-5）。

### 対象メーカー / システム

| メーカー | リモートシステム | 備考 |
|---|---|---|
| Medtronic | CareLink | |
| Abbott | Merlin.net | |
| Boston Scientific | LATITUDE | |
| MicroPort | — | |
| WCD | ZOLL LifeVest 等 | 装着型自動除細動器。既存商用製品が未対応で、自社開発の主要動機のひとつ |

Biotronik は現時点で対象外（院内で扱いがあれば追加）。**要確認事項**。

### スコープ外（現時点）

- 電子カルテとの直接連携（API/HL7/SS-MIX2）。まずはクリップボード/CSVでの手動転記支援に留める
- 各社システムからのデータ自動取得（API連携）。ORFICE等の商用製品はここを実装しているが、
  各社との契約・接続が必要なため自社開発の初期スコープには含めない
- 患者向け機能

## 1.4 機能要件

### FR-1 レポート取り込み

- **フォルダごとの一括取り込みができる**（ドラッグ&ドロップ、100件規模）。
  レポートはUSBメディアでまとめて持ち込まれるため、これが主要な使い方になる
  （[02.2](02-architecture.md#22-ネットワーク構成とデータ動線)）
- 一括処理の結果を一覧表示し、成功／要確認／失敗を件数と内訳で示す
- 取り込み時にメーカーを自動判別する（判別失敗時は手動選択）
- 同一レポートの重複取り込みを検出する（ファイルハッシュ＋患者ID＋レポート日）。
  USB経由では同じファイルを再度持ち込む事故が起きやすいため必須
- USBメディアへの書き込みは行わない（[05.7](05-security-and-compliance.md#57-usb経由のファイル持ち込み)）

### FR-2 項目抽出

- スキャンPDF（画像のみ）からOCRで項目を抽出する
- テキストレイヤーを持つPDFの場合はOCRを使わずテキストを直接利用する
- 抽出項目は [04. データモデル](04-data-model.md) の共通スキーマに正規化する
- 各抽出値に信頼度スコアを付与する

### FR-3 確認・修正

- 抽出結果を元PDFの該当箇所と並べて表示し、人が確認・修正できる
- 信頼度が閾値未満の項目は視覚的に強調し、未確認のまま確定できないようにする
- 修正内容を記録し、抽出ルール改善のフィードバックに使えるようにする

#### 前回値との差分の可視化

各項目について、**過去の推移と前回からの変化を視覚的に示す。**

| 表示 | 内容 |
|---|---|
| スパークライン | 直近6回分の推移をミニグラフで表示。今回値を強調 |
| 差分 | 前回値との差を実数と変化率で表示（例: `▲ +3回 (+27.3%)`） |
| 変化サマリ | 画面上部に「注意すべき変化」だけを抜き出して表示 |
| 絞り込み | 「変化のあった項目だけ表示」で確認作業を短縮 |

**変化の意味は項目によって異なる**ため、項目ごとに設定を持つ。

| 設定 | 意味 | 例 |
|---|---|---|
| `dir` | 臨床的に注意すべき変化の向き | 閾値・AF burden は**上昇**が注意／P波高・R波高は**低下**が注意／インピーダンスは**どちらも**注意 |
| `tol` | 何%の変化から「注意」とみなすか | — |

> **注意:** 現在モックに入っている `dir` / `tol` の値はすべて**仮の値**。
> 臨床的に妥当な設定は現場で確認して決める。値はコードに埋め込まず、設定として外出しする。

**システムは数値の変化を提示するだけで、臨床判断は行わない。**
「異常」「要治療」といった判定は表示せず、変化の事実と大きさのみを示す。

##### なぜ差分表示に価値があるのか

1. **確認作業が速くなる。** 変化のない項目は流し見でよく、変わったところだけ見ればよい
2. **OCR誤認の検出になる。** 前回76ヶ月→今回740ヶ月のような桁誤りが一目で分かる
   （[03.7](03-extraction-design.md#37-h-信頼度の設計) の整合チェック）
3. **単発のPDF変換ツールにはできない。** 過去データを持つ一元管理システムだからこそ成立する

### FR-4 出力

- カルテ転記用のテキストを定型フォーマットで生成し、クリップボードにコピーできる
- テンプレートは院内で編集可能にする（コード変更なしで文面を変えられる）
- CSV / Excel でのエクスポート

### FR-5 デバイス台帳

**本システムは遠隔モニタリングの支援ツールであると同時に、院内CIEDの台帳でもある。**
遠隔モニタリングをしていない患者（外来チェックのみ）も登録対象に含める。

- 全CIED患者・デバイスを登録し、一覧・検索できる
- **遠隔モニタリングの有無で絞り込める**（遠隔中 / 未導入 / 中止）
- 遠隔なし患者は、外来チェックの結果を手入力またはレポート取り込みで更新する
- 既存の台帳（Excel等）から**CSVで一括登録**できる（初期データ投入に必須）
- レポート取り込み時、未登録の患者・デバイスは自動で台帳に追加する
- **リコール・安全性情報の該当患者を抽出できる**（メーカー・機種・シリアル範囲・植込み日範囲で検索）

#### なぜ台帳まで持つのか

遠隔分だけを管理しても、院内のCIED患者の全体像は分からない。台帳を兼ねることで:

| できること | 価値 |
|---|---|
| リコール／アドバイザリ発出時に該当患者を数秒で抽出 | 紙台帳・Excelを追う作業がなくなる。**対応の遅れは患者安全に直結する** |
| 遠隔・外来を問わずフォロー漏れを検出 | 「最終フォロー日」を統一して扱えば、全患者で漏れが拾える |
| 遠隔モニタリングの導入候補を抽出 | 未導入患者のうち適応がある人を見つけられる |
| 電池消耗が近い患者の把握 | 交換手術の計画が立てやすい |
| MRI撮像可否の即答 | 他科からの問い合わせに台帳で答えられる |

**商用製品（ORFICE / CardioAgent Pro）は遠隔モニタリングの管理が主眼で、
遠隔をしていない患者を含めた院内全体の台帳としては設計されていない。**
WCD対応と並ぶ、自社開発の主要な理由になる。

### FR-6 外来準備シート

電子カルテから当日の患者IDをまとめてコピーし、貼り付けるだけで外来準備用の一覧を作る。

#### 入力

- テキストエリアに**複数の患者IDを一括で貼り付ける**
- 電子カルテからのコピーは、氏名・予約時刻・見出し行などが混ざる前提で設計する

##### 患者IDの形式（確定）

**7桁の数字。先頭ゼロが意味を持つ**（例: `0012339`、`1234567`）。

> ⚠️ **患者IDは必ず文字列として扱い、数値に変換しないこと。**
> 数値化すると `0012339` が `12339` になり、別人と取り違える。以下すべてが事故ポイント:
>
> | 箇所 | 対策 |
> |---|---|
> | DBの型 | `INTEGER` ではなく `TEXT` にする |
> | JSON / API | 数値型で受け渡さない |
> | **CSV取込（台帳の初期投入）** | **Excelで開くと先頭ゼロが消える。** Excelを経由させない運用にするか、取込時に桁数を検証して7桁未満を弾く |
> | 突合処理 | 比較前にゼロ埋めを揃える |
>
> この1点だけで患者取り違えが起きうるため、実装時のチェック項目として明示する。

##### 正規化と抽出のルール

| 処理 | 内容 |
|---|---|
| 文字の正規化 | 全角数字 → 半角 |
| 抽出 | 連続する数字列のうち**ちょうど7桁のものだけ**を採用。6桁以下・8桁以上（日付 `20260821`、電話番号など）は自動的に除外される |
| 1行に複数のID | **すべて拾う。** カンマ・スペース区切りで並んでいても取りこぼさない |
| 区切り | 改行・タブ・カンマ・スペースの混在を許容 |
| 重複 | 除去する。除去した件数を表示する |
| 順序 | **貼り付け順を保持する**（＝受診順であることが多いため、既定の並び順にする） |

**「1行1件」ではなく「7桁を全部拾う」を選んだ理由:**
取りこぼし（＝患者の見落とし）は静かに起きて気づけないが、余分に拾った場合は
「台帳に登録がない患者ID」として画面に出るため人が気づける。安全側に倒している。

#### 出力

- 台帳と照合し、患者ごとにデバイス情報・最終フォロー・電池状況・確認事項を表示する
- **台帳に登録がない患者IDは別枠で明示する**（新規植込み・他院植込み・ID入力誤りの可能性）。
  黙って無視しない
- **列見出しのクリックで並べ替えできる**。「貼り付け順に戻す」を用意する
- 要対応の患者は行を色分けする
- **メーカー別の人数を集計する** — 当日必要なプログラマの台数把握に使う
- 印刷レイアウトに対応する（紙で持ち歩く運用を想定）
- CSV出力

#### なぜ台帳と繋がっていると効くのか

外来準備は本来、患者ごとに台帳やカルテを引いて回る作業になる。
台帳が既にあるため、**IDを貼るだけで必要な情報が揃う**。
特にメーカー別の集計は、遠隔・非遠隔を問わず全患者が台帳に載っていて初めて正確になる。

      （見出し行・時刻・氏名の混ざり方。**実際にコピーしたテキストを見せてもらうのが最短**。
      その際は患者IDと氏名をダミーに置き換えてもらう）

### FR-7 一元管理

- 患者・デバイス単位でレポート履歴を時系列に閲覧できる
- バッテリー残量、閾値、インピーダンス等の推移をグラフ表示する
- 未送信・未確認レポートを一覧で把握できる（フォロー漏れ防止）

### FR-8 マルチユーザー（Phase 2。**Phase 1 では実装しない**）

Phase 1 は本人1人での単独運用と決定したため、認証・権限・同時アクセスは実装しない
（[02.3](02-architecture.md#23-配置構成)）。

- 複数人が同時にアクセスできる
- ユーザーごとの権限（閲覧のみ / 編集 / 管理）
- 誰がいつ何を確認・修正したかの操作ログ

## 1.5 非機能要件

| ID | 要件 | 内容 |
|---|---|---|
| NFR-1 | **完全オフライン** | 外部ネットワークへの通信を一切行わない。OCRモデル・辞書はすべて同梱。テストで通信の不在を検証する（[05](05-security-and-compliance.md)） |
| NFR-2 | **対応OS** | Windows（院内PC）。開発・検証はmacOSでも行うため、実装はクロスプラットフォームを維持する |
| NFR-3 | **導入容易性** | IT担当者不在を前提。インストーラー1本、ダブルクリック起動。外部ソフトの別途インストールを要求しない |
| NFR-4 | **性能** | 1ページのレポート1件あたり、取り込みから抽出完了まで10秒以内（目標）。100件バッチで実用的な時間に収まること |
| NFR-5 | **精度** | 主要項目の抽出正解率95%以上（目標）。ただし**未達でも人の確認で担保する設計**とし、精度だけに依存しない |
| NFR-6 | **可搬性** | データはSQLiteファイル/DBダンプでバックアップ・移行できる |

### NFR-4/5 の数値について

現時点では**根拠のない目標値**。サンプル帳票でOCR精度を実測してから確定する。
実測前にこの数値を約束しないこと。

## 1.6 受入基準（Phase 1 プロトタイプ）

- [ ] 各メーカー1枚ずつの実帳票（黒塗り済み）で、定義した必須項目が抽出できる
- [ ] 抽出結果の確認画面で、誤りを人が修正できる
- [ ] カルテ転記用テキストがクリップボードに出力でき、実際の転記作業が短縮されることを現場で確認できる
- [ ] ネットワークを切断した状態で全機能が動作する
