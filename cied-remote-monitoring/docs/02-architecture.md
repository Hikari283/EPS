# 02. アーキテクチャ

## 2.1 段階計画

「まず単体アプリ、あとで共有システム」という方針を、**作り直しが発生しない形**で実現する。

| Phase | 形態 | 目的 |
|---|---|---|
| **0** | CLI + 評価スクリプト | OCR精度・抽出精度の実測。UIなし。開発者が回す |
| **1** | ローカルWebアプリ（1台完結） | 現場での実用性検証。exe化して1台にインストール |
| **2** | 院内サーバー + Webアプリ | 複数人共有。UIはPhase 1のものをそのまま使う |

### 作り直しを避けるための2つの設計判断

**判断1: UIは最初からブラウザ**

デスクトップGUI（Tkinter/PySide）で作ると Phase 2 で全面書き直しになる。
Phase 1 では exe が `localhost` でサーバーを起動し、既定ブラウザを開く方式にする。
利用者から見れば「ダブルクリックで起動してアプリが開く」で違いはない。
Phase 2 は同じアプリを院内サーバーに置き、各PCはブラウザで接続するだけ。

**判断2: コアロジックをUIから完全に分離**

`core/` （PDF処理・OCR・抽出・正規化）は UI・DB・Web を一切知らない純粋なライブラリにする。
CLI もWebアプリも同じ `core` を呼ぶ。これにより Phase 0 の評価スクリプトがそのまま
回帰テストとして生き続ける。

## 2.2 ネットワーク構成とデータ動線

**院内ネットワークはインターネット系と電子カルテ系が分離されており、両者は連携していない。**
各社リモートモニタリングシステムはインターネット系からしか到達できず、
両ネットワーク間のファイル移動は **USBメディア経由**で行う。

```
┌─ インターネット系ネットワーク ─────────────────────┐
│   各社リモートシステム                                │
│   (CareLink / Merlin.net / LATITUDE /                │
│    MicroPort / LifeVest)                             │
│         │  レポートPDFをまとめてダウンロード            │
│         ▼                                            │
│   作業PC                                              │
└─────────┬────────────────────────────────────────────┘
          │  USBメディア（手運び）
┌─────────▼────────────────────────────────────────────┐
│  電子カルテ系ネットワーク（閉域）                        │
│                                                       │
│   本システム（サーバー または 常時起動PC）                │
│     一括取り込み → 抽出 → 確認・修正 → 転記テキスト生成   │
│         │                                             │
│         │  クリップボード                                │
│         ▼                                             │
│   電子カルテ端末（ブラウザで本システムを開く）             │
└───────────────────────────────────────────────────────┘
```

### この構成が設計に与える影響

**1. 「印刷→スキャン」をやめる価値は失われない**

ネットワークが繋がっていなくても、**USBで運んだPDFはテキストレイヤーを保持したまま**届く。
避けたかったのは「紙にすること」であって、ネットワーク直結は手段にすぎない。
USBコピー1回 vs 全レポートの印刷+スキャン、では手間も精度も後者が圧倒的に不利。

→ [03. 抽出エンジン設計](03-extraction-design.md) のテキストレイヤー優先方式はそのまま有効。
**むしろこれが主経路になり、OCRはフォールバックに後退する可能性が高い。**
M1（精度検証）の不確実性が大きく下がる。

**2. 一括取り込みUIが必須機能になる**

USB経由なら「1ファイルずつ」ではなく「フォルダごと100件」が自然な単位。
フォルダのドラッグ&ドロップによるバッチ取り込みと、処理結果の一覧表示を Phase 1 の必須機能とする。
（[01. FR-1](01-requirements.md#fr-1-レポート取り込み) の優先度を引き上げ）

**3. UIをブラウザにした判断がここで効く**

電子カルテ端末は多くの場合、任意のソフトをインストールできない。
本システムを電子カルテ系ネットワーク上のサーバー（または常時起動PC）に置き、
カルテ端末からはブラウザでアクセスしてクリップボードにコピーする動線が取れる。
デスクトップアプリだとこれができず、別画面を見ながら手打ちに逆戻りする。

**4. USBは院内で最も警戒される経路**

国内の医療機関でUSB・保守回線を起点とするランサムウェア被害が複数発生しており、
閉域ネットワークへのUSB持ち込みは規程で禁止・制限されていることが多い。
**技術的に可能かではなく、規程上許されるかを情報システム部門に確認する必要がある**
（[05.7](05-security-and-compliance.md#57-usb経由のファイル持ち込み)）。

### 決定事項

- USBは**院内専用メディア**を使用する（私物・ベンダー配布品は使わない）
- 本システムは**電子カルテ系ネットワークの共有ファイル領域**に置く

## 2.3 配置構成

### Phase 1 の形: 単独運用（決定）

**まず本人1人だけで使う。** 共有は Phase 2 へ後送りする。

```
[電子カルテ系ネットワーク]

  本人のPC 1台
    ├─ 本システム（アプリ + DB + 原本PDF）  ← すべてこのPCのローカルディスク
    │      ↑ ブラウザで localhost にアクセス
    └─ 電子カルテ
           ↑ クリップボードで転記テキストを貼り付け
```

この形にすると、以下が**まるごと不要**になる。

| 不要になるもの | 理由 |
|---|---|
| サーバー役PCの確保 | 自分のPCで完結する |
| ポート開放・ファイアウォール設定の許可 | localhost のみで外部から接続しない |
| ユーザー認証・権限管理 | 利用者が1人 |
| DB破損対策（下記） | 書き込むプロセスが元から1つ |
| ネットワーク越しのアクセス確認 | 不要 |

情報システム部門への依頼が「1台にソフトを入れてよいか」だけになる。
**効果が出るか分からない段階でサーバー設置の承認を取りに行くと話が重くなるため、
まず1台で効果を実証してから広げるのが確実。**

UIはこの段階でもブラウザ（localhost）にしておく。
利用者から見れば「ダブルクリックで起動してアプリが開く」で違いはなく、
Phase 2 で共有に広げるときにUIを作り直さずに済む。

#### 確認が必要な点

**転記テキストのクリップボード貼り付けは、本システムと電子カルテが同じPCで開ける場合にのみ成立する。**
電子カルテが別の専用端末でしか開けない場合、画面を見ながらの手打ちに戻ってしまい、
時間短縮効果が大きく削がれる。ここは事前に確認しておくこと。

---

以下は Phase 2（複数人共有）へ進むときの設計。**Phase 1 では不要。**

### 「共有フォルダに置く」で壊れるもの

配置先が電子カルテ系ネットワークであることは正しい。転記先がそこにある以上、
システムも同じ側になければ意味がない。

ただし **「DBファイルを共有フォルダに置き、複数人が同時に開く」は絶対に避ける。**

ネットワーク共有（SMB）上のファイルロックは不完全で、複数プロセスが同時に書き込むと
DBファイルが破損する。これはAccessやSQLiteの共有フォルダ運用で古くから知られた事故パターンで、
**100台以上のレポート履歴が一度に失われうる**。予兆なく起きるうえ、復旧が難しい。

同じ理由で、実行ファイル一式を共有フォルダに置いて各PCから直接起動する形も推奨しない
（起動が遅い、ウイルス対策ソフトのスキャンで詰まる、更新中に他の人が掴んでいて差し替えられない）。

### 推奨する形: 常時起動PC 1台を「サーバー役」にする

専用のサーバー機材は不要。**電子カルテ系ネットワーク上の、常時起動できるWindows PC 1台**があればよい。

```
[電子カルテ系ネットワーク]

  サーバー役PC（常時起動）
    ├─ 本システム（アプリ本体）      ← ローカルディスクに置く
    ├─ データベース                  ← ローカルディスクに置く（重要）
    └─ 原本PDF保管
         │
         │  ブラウザでアクセス  http://<サーバー役PCの名前>:ポート
         │
    ┌────┴─────┬──────────┐
  技師PC     カルテ端末    医師PC
  取り込み・  転記テキストを  閲覧
  確認・修正  コピー&貼付
```

| 置き場所 | 何を置くか | 理由 |
|---|---|---|
| サーバー役PCのローカルディスク | アプリ本体、DB | 同時書き込みによる破損を防ぐ。書き込むプロセスは常に1つ |
| 共有ファイル領域 | **バックアップ**、エクスポートしたCSV | ここは複数人が読むだけなので安全 |
| 各PC | 何も置かない | ブラウザだけあればよい |

DBへの書き込みを行うプロセスを1つに限定するのが要点。
利用者から見れば「共有フォルダにあるものを皆で使う」のと変わらないが、破損リスクが消える。

### 注意: 電子カルテベンダーの管理領域には置かない

「カルテのファイルの中」が、電子カルテソフト自身が管理しているフォルダを指す場合は要注意。

- ベンダーのアップデートで中身が消える・上書きされる可能性がある
- 保守契約上、管理領域に第三者のファイルを置くことが問題になる場合がある
- 障害時に「原因の切り分けができない」として保守対象外にされうる

**電子カルテとは無関係の独立したフォルダ（または独立したPC）を用意してもらうこと。**
同じネットワーク上にあれば目的は達せられる。

### 未確認事項

Phase 1（単独運用）に必要なもの:

- [ ] 自分のPCに実行ファイルをインストールしてよいか（情報システム部門の許可）
- [ ] **本システムと電子カルテを同じPCで開けるか**（クリップボード転記が成立する条件）
- [ ] 各社リモートシステムからPDFを直接ダウンロードできるか（メーカーごとに可否が異なる可能性）

Phase 2（共有）へ進むときに必要なもの:

- [ ] 常時起動できるPCを1台確保できるか（サーバー役）
- [ ] そのPCでポートを開けられるか（Windowsファイアウォールの設定、情報システム部門の許可）
- [ ] 電子カルテ端末のブラウザから、そのPCにアクセスできるか
- [ ] 配置先が電子カルテベンダーの管理領域でないか

## 2.5 技術選定

### 言語・ランタイム

**Python 3.12**。OCR/画像処理/PDFのエコシステムが最も厚く、Windows exe 化の実績もある。

### PDF → 画像

| 候補 | ライセンス | 判断 |
|---|---|---|
| **pypdfium2** | Apache-2.0 / BSD-3 | **採用**。ライセンスがクリーンで、外部バイナリ不要（wheelに同梱）、描画も速い |
| PyMuPDF (fitz) | AGPL-3.0 または商用 | 高機能だがAGPL。院内利用なら実務上は問題になりにくいが、将来の配布形態を縛るので避ける |
| pdf2image | MIT（ただし poppler 外部依存） | poppler の別途インストールが必要 → NFR-3（導入容易性）に反する |

### OCRエンジン

**結論: 1つに決め打ちしない。** `core/ocr/base.py` に共通インターフェースを定義し、
実装を差し替えられるようにした上で、サンプル帳票で実測して決める。

```python
class OcrEngine(Protocol):
    def recognize(self, image: np.ndarray) -> list[OcrToken]: ...

@dataclass
class OcrToken:
    text: str
    bbox: tuple[int, int, int, int]   # x0, y0, x1, y1（画像座標）
    confidence: float                  # 0.0–1.0
```

候補:

| 候補 | オフライン | Mac/Win | 日本語精度の見込み | 懸念 |
|---|---|---|---|---|
| **Tesseract 5** (`jpn`, `jpn_vert`, `eng`) | ○ | ○ | 中 | 数字の誤認（0/O, 1/l, 5/S, 6/8）が起きやすい。ホワイトリスト指定と辞書で緩和可能 |
| **PaddleOCR (japan)** | ○（モデル同梱すれば） | ○ | 高 | モデルサイズ大。初回DLを避けるため同梱が必須。ONNX Runtime 化でCPU実用速度を狙う |
| Windows.Media.Ocr | ○ | Winのみ | 中〜高 | 追加インストール不要という利点は大きいが、macOSで動かず開発サイクルが回しにくい。**補助枠** |
| YomiToku | ○ | ○ | 高 | 日本語文書特化で有力だが重く、CPU推論が実用速度に乗るか要検証 |

**第一候補は Tesseract**（軽い・Windowsインストーラーが整っている・PyInstaller同梱の実績が豊富）。
ただし帳票の数値精度が要件を満たさない場合、PaddleOCR(ONNX)へ切り替える。
この判断はサンプル入手後の実測で行う。

> 現実的な見立て: CIEDレポートの重要項目（数値・単位・英字パラメータ名）は日本語文章よりも
> 認識しやすい部類。一方で表罫線・網掛け・スキャンの汚れが効くので、**前処理の作り込みが
> エンジン選定より効く可能性が高い**。

### 画像前処理

**OpenCV (opencv-python-headless)**。傾き補正、二値化、ノイズ除去、解像度正規化。
詳細は [03](03-extraction-design.md)。

### Webフレームワーク

**FastAPI + Jinja2 テンプレート + 素のHTML/CSS/JS**（軽量）。

SPA（React等）は導入しない。理由: ビルドチェーンが増えるとオフライン配布とインストーラー化が
複雑になり、NFR-3 に反する。画面数も多くない。

グラフ描画は **Chart.js をローカル同梱**（CDN参照は NFR-1 違反）。

### データベース

**SQLAlchemy 2.x** でORMを挟み、Phase 0-1 は SQLite、Phase 2 は PostgreSQL へ移行する。
マイグレーションは **Alembic**。

SQLite を共有フォルダに置いて複数人アクセス、は**やらない**（ファイルロック起因の破損リスク）。
Phase 2 は必ずサーバープロセス経由にする。

### パッケージング

```
PyInstaller (onedir)  →  Inno Setup  →  setup.exe
```

- `onefile` ではなく `onedir` を使う（起動が速く、OCRモデル等の大きな同梱物と相性が良い）
- Tesseract 本体・言語データ、OCRモデル、Chart.js をすべて同梱する
- **Windows実機でビルドが必要**。macOS上ではWindows用exeは作れない
- スタートメニュー/デスクトップにショートカット、アンインストーラーを用意

## 2.7 却下した選択肢と理由

| 選択肢 | 却下理由 |
|---|---|
| クラウドOCR（Google Vision, Azure Document Intelligence 等） | NFR-1（完全オフライン）に真っ向から反する。精度は明確に上だが選択肢に入らない |
| デスクトップGUI（PySide6/Tkinter） | Phase 2 の共有システム化でUIを全面作り直しになる |
| Electron / Tauri | Pythonのビルドチェーンに加えてNode/Rustが必要になり、配布とメンテのコストが要員体制に合わない |
| SQLiteを共有フォルダに置いて複数人で共有 | 同時書き込みでDB破損の実績が多い。医療データで取れないリスク。代替は [2.3](#23-配置構成) の「常時起動PC 1台をサーバー役にする」 |
| 実行ファイル一式を共有フォルダに置き各PCから起動 | 起動が遅い、ウイルス対策のスキャンで詰まる、更新時にファイルを掴まれて差し替えられない |
| 商用製品（ORFICE / CardioAgent Pro）の採用 | 検討済み。WCD非対応と院内フローへの適合性から自社開発を選択（[01](01-requirements.md)） |

## 2.8 商用製品との機能差の自覚

ORFICE / CardioAgent Pro は各社データセンターとのAPI連携でデータを自動収集している。
**本システムはPDF読み取りベースなので、データ取得の自動化度では明確に劣る。**

勝てるのは以下の3点。ここに集中し、API連携の再発明はしない。

1. **WCDを含む院内の全デバイスを1か所で見られる**
2. **遠隔をしていない患者も含めた台帳になる**（[01. FR-5](01-requirements.md#fr-5-デバイス台帳)）。
   商用製品は遠隔モニタリングの管理が主眼で、院内CIED全体の台帳としては設計されていない。
   リコール発出時の該当患者抽出は、台帳に全デバイスが載っていて初めて成立する
3. **院内フローに合わせた出力文面**

ただし [2.2](#22-ネットワーク構成とデータ動線) のネットワーク分離は商用製品にとっても制約になる。
API自動収集はインターネット系からしか行えないため、電子カルテ系へデータを渡すには
何らかの中継（DMZ設置、専用回線、あるいは同じくUSB）が必要になるはず。
**商用製品を再検討する場合は、「自院のネットワーク構成でどう繋ぐのか」を必ず具体的に確認すること。**
カタログ上の機能が自院で使えるとは限らない。
