# CIED遠隔モニタリング デバイス一元管理システム

心臓植込み型電気デバイス(CIED)の遠隔モニタリングレポートPDFから必要項目を自動抽出し、
カルテ転記の時間短縮とDrとの情報共有を実現する、院内向けの完全オフラインシステム。

**同時に、院内CIEDの台帳としても機能する。** 遠隔モニタリングをしていない患者
（外来チェックのみ）も登録対象とし、遠隔の有無で絞り込める。
リコール発出時の該当患者抽出やフォロー漏れの検出は、全デバイスが載っていて初めて成立する。

## 画面イメージ

[mockups/ui-mockup.html](mockups/ui-mockup.html) をブラウザで開くと、
5画面（取り込み／確認・修正／カルテ転記／デバイス台帳／外来準備シート）の
モックアップを確認できる。ダミーデータのみ。

一部は実際に動く（確認画面の該当箇所ハイライト、台帳の遠隔有無の絞り込み、
外来準備シートの患者ID貼り付け・照合・並べ替え）。

## ラベル抽出スクリプト

M1（抽出ルール作成）の最初の一歩。PDFから項目名らしき文字列を一覧CSVに出す。
値そのものは扱わない（項目名は個人情報ではないため、そのまま目視確認できる）。

```bash
pip install -e ".[dev]"
python -m cli.list_labels report1.pdf report2.pdf --out labels.csv
```

出力後は必ず `labels.csv` を目視確認し、患者の識別情報が紛れていないか確かめること
（詳細は [docs/06-roadmap.md 6.1-E](docs/06-roadmap.md#6.1-次にやること2026-08-20-時点)）。

## 設計上の重要な判断（サマリ）

1. **UIは最初からローカルWebアプリ**（FastAPI + ブラウザ）。単体アプリでも `localhost` で動かし、
   Phase 2 の「複数人共有」へ移行するときにUIを作り直さずに済ませる。
2. **OCRエンジンは差し替え可能な抽象インターフェース**にする。Tesseractを第一候補とするが、
   日本語スキャン帳票での精度は実測してから決める（サンプル入手が前提）。
3. **抽出ルールはコードに埋めずYAMLプロファイルに外出し**。メーカー追加＝YAML追加で済む形にする。
4. **全自動を目指さない。** 抽出値には信頼度を付け、閾値未満は「要確認」として人が必ず目視する
   UI前提の設計にする。医療データの誤転記リスクを構造的に防ぐ。
5. **「印刷→スキャン」は廃止する。** 各社システムからPDFを直接取得できることを確認済み。
   ネットワークは分離されているが、USBで運んだPDFはテキストレイヤーを保持したまま届く。
   **これによりOCRは主経路から外れ、フォールバックに後退した。**
   当初の最大リスク（スキャン品質によるOCR精度不足）はほぼ解消している
   （[03.2](docs/03-extraction-design.md#決定-pdfの直接取得が可能)）。

## 前提となるネットワーク構成

院内はインターネット系と電子カルテ系が**分離**されており、両者は連携していない。
各社リモートシステムはインターネット系からのみ到達可能で、
両ネットワーク間のファイル移動はUSBメディア経由で行う。
詳細と設計への影響は [02.2](docs/02-architecture.md#22-ネットワーク構成とデータ動線)。

決定済み:

- USBは**院内専用メディア**を使用する
- 本システムは**電子カルテ系ネットワーク側**に置く
- **Phase 1 は本人1人での単独運用**（自分のPC 1台で完結。共有は Phase 2 へ後送り）

単独運用のため、Phase 1 では認証・サーバー設置・ポート開放・DB共有が
すべて不要になる。詳細は [02.3 配置構成](docs/02-architecture.md#23-配置構成)。
