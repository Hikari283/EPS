# CIED遠隔モニタリング デバイス一元管理システム

心臓植込み型電気デバイス(CIED)の遠隔モニタリングレポートPDFから必要項目を自動抽出し、
カルテ転記の時間短縮とDrとの情報共有を実現する、院内向けの完全オフラインシステム。
**自動抽出はMedtronicのみ対応**（2026/08/21決定。[01.要件定義](docs/01-requirements.md#対象メーカー--システム)）。
不整脈イベントの検出・分類やコメント文の自動生成も対象外で、人が手動で記載する。

**同時に、院内CIEDの台帳としても機能する。** こちらは全メーカー対象。遠隔モニタリングを
していない患者（外来チェックのみ）も登録対象とし、遠隔の有無で絞り込める。
リコール発出時の該当患者抽出やフォロー漏れの検出は、全デバイスが載っていて初めて成立する。

## 使い方（Pythonのインストール不要）

**2026/08/21 決定: PythonはこのPCにインストールしない方針にした。** 代わりに
単体HTMLファイル（ブラウザだけで動く。インストール・通信一切不要）を使う。

### `cied_app.html`（本体・こちらを使う）

レポート取り込み・デバイス台帳・遠隔モニタリング記録・外来準備シートを1つにまとめたアプリ。
台帳は`localStorage`に保存され、ブラウザを閉じても残る。

1. `cied_app.html` をこのPCに置く（ダブルクリックでブラウザが開く）
2. 「①レポート取り込み」タブ: CareLinkレポートをPDFビューアで開き、**Ctrl+A**→**Ctrl+C**でコピー。
   「クリップボードから読み込む」を押すか、テキストエリアに**Ctrl+V**で貼り付けると自動で抽出される。
   抽出直後からカルテ文の下書きが画面下に表示され、項目を直すと下書きも連動して更新される
   （保存はまだされていない）
3. 患者ID・氏名・デバイス種別を確認し、抽出結果を確認・修正してから
   「確定して台帳に保存＋カルテ文を生成」。ここで初めて台帳・レポート記録に反映される
4. 「②デバイス台帳」タブ: 全メーカーのデバイスを登録・編集・検索・絞り込み・削除できる。
   CSV取込／出力にも対応（他メーカーはここから手動登録する）。各行の「カルテ文」ボタンで、
   新しく貼り付けなくてもその患者の現時点の合成カルテ文をいつでも確認できる
5. 「③遠隔モニタリング記録」タブ: 確定したレポートの取り込み履歴を日付順に一覧表示。
   台帳が「患者ごとの現在の状態」であるのに対し、こちらは「いつ・誰のレポートを取り込んだか」の履歴
6. 「④外来準備シート」タブ: 電子カルテから患者IDをコピペすると台帳と照合した一覧が出る。
   直近のレポートで保存したリード値も一緒に表示され、その場で数値の手直しや
   「Dr Call」「当日メモ」の書き込みもできる（この画面での編集はその場限り）

**同じ患者のページをバラバラの順番（Aさん→Bさん→Aさんの続き、など）で読み込んでも大丈夫。**
確定するたびに、その患者のこれまでの全レポートを項目ごとに合成した、最も完全なカルテ文が作られる。

**レポート取り込みは台帳の項目（MRI可否・担当医・備考など）を上書きしない。**
機種名・シリアル番号・遠隔状況・最終フォロー日だけを更新する
（[04.2](docs/04-data-model.md#42-台帳のデータモデル)の設計どおり。動作確認済み）。

### `carelink_extractor.html`（単機能版・軽く試したいとき用）

抽出結果を見るだけで、台帳への保存はしない単機能版。使い方は`cied_app.html`の①と同じ。

### 共通

**どちらのページもインターネット通信を一切行わない。** ブラウザの中だけでJavaScriptが動いていて、
貼り付けた内容・保存したデータはどこにも送信されない（開発者ツールのネットワークタブで確認可能）。
インストール・USB持ち込み・pip・ライブラリのダウンロードは一切不要。

抽出ルールは `src/profiles/medtronic_carelink.yaml` と同じもの
（Python版として先に作り、実データで動作確認してからJavaScriptに移植した）。
実際のレポート3ページ分の実データで自動テスト済み（詳細は
[docs/06-roadmap.md](docs/06-roadmap.md)）。

## 設計上の重要な判断（サマリ）

1. **UIは最初からローカルWebアプリ**（FastAPI + ブラウザ）。単体アプリでも `localhost` で動かし、
   Phase 2 の「複数人共有」へ移行するときにUIを作り直さずに済ませる。
2. **OCRエンジンは差し替え可能な抽象インターフェース**にする。Tesseractを第一候補とするが、
   日本語スキャン帳票での精度は実測してから決める（サンプル入手が前提）。
3. **抽出ルールはコードに埋めずYAMLプロファイルに外出し**。メーカー追加＝YAML追加で済む形にする。
4. **全自動を目指さない。** 抽出値には信頼度を付け、閾値未満は「要確認」として人が必ず目視する
   UI前提の設計にする。医療データの誤転記リスクを構造的に防ぐ。
5. **「印刷→スキャン」は廃止する。** 各社システムからPDFを直接取得できることを確認済み。
   ネットワークは分離されているが、USBで運んだPDFはテキストレイヤーを保持したまま届く。
   **これによりOCRは主経路から外れ、フォールバックに後退した。**
   当初の最大リスク（スキャン品質によるOCR精度不足）はほぼ解消している
   （[03.2](docs/03-extraction-design.md#決定-pdfの直接取得が可能)）。

## 前提となるネットワーク構成

院内はインターネット系と電子カルテ系が**分離**されており、両者は連携していない。
各社リモートシステムはインターネット系からのみ到達可能で、
両ネットワーク間のファイル移動はUSBメディア経由で行う。
詳細と設計への影響は [02.2](docs/02-architecture.md#22-ネットワーク構成とデータ動線)。

決定済み:

- USBは**院内専用メディア**を使用する
- 本システムは**電子カルテ系ネットワーク側**に置く
- **Phase 1 は本人1人での単独運用**（自分のPC 1台で完結。共有は Phase 2 へ後送り）

単独運用のため、Phase 1 では認証・サーバー設置・ポート開放・DB共有が
すべて不要になる。詳細は [02.3 配置構成](docs/02-architecture.md#23-配置構成)。
